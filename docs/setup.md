# 導入手順（Setup Guide）

本ドキュメントは、Google Workspace 組織内に GAS Artifact Hub を新規導入するためのセットアップ手順を説明します。

---

## 1. 導入の前提条件

- **実行環境**: 同一 Google Workspace ドメイン内での 1 組織 1 デプロイ。
- **非対応**: 個人 Gmail（`@gmail.com` 等）、社外アカウントへの共有、Google グループの展開による ACL 設定。
- **デプロイ担当アカウント**:
  - Google Apps Script の実行、Google Drive へのファイル作成、OAuth 権限の承認が組織ポリシーで許可されている管理者用アカウント。
  - Web アプリはデプロイ担当アカウントの権限とクォータで動作します（「次のユーザーとして実行：自分」）。
  - 不要な業務機密フォルダへのアクセス権を持たない、本システム管理用のアカウントを推奨します。
- **権限分離の最重要原則**:
  - **管理用スプレッドシート（DB）、専用保存 Drive フォルダ、Apps Script プロジェクトを一般社員へ絶対に直接共有しないでください**。
  - 一般社員は Web アプリ（`/exec`）経由でのみデータにアクセスし、システム内部で ACL 判定が行われます。直接共有すると、シートの直接編集による ACL 迂回や不正書き換えが可能になってしまいます。

---

## 2. 新規スプレッドシートからの手動セットアップ

### ステップ 1: 管理用スプレッドシートの作成
1. 管理者アカウントで Google ドライブを開き、新しいスプレッドシートを作成します。
   - 既存の業務シートと混在させず、完全に独立した新規シートを用意してください。
   - 名称例: `GAS Artifact Hub System`

### ステップ 2: 本番ソースコードの配置
1. スプレッドシートのメニューから **拡張機能 → Apps Script** を開きます。
2. デフォルトの空ファイル `Code.gs` を削除します。
3. 本リポジトリの `src/` 配下にあるすべての本番ファイル（計 13 ファイル）を同名で作成・配置します：
   - **スクリプト（`.gs`）**:
     - `Constants.gs`
     - `Setup.gs`
     - `DriveStore.gs`
     - `Scanner.gs`
     - `Audit.gs`
     - `Store.gs`
     - `Main.gs`
   - **HTML（`.html`）**:
     - `Upload.html`
     - `UploadCss.html`
     - `UploadJs.html`
     - `Shell.html`
     - `ShellCss.html`
     - `ShellJs.html`
4. 左メニューの歯車アイコン（**プロジェクトの設定**）を開き、「`appsscript.json` マニフェスト ファイルをエディタで表示する」にチェックを入れます。
5. エディタに戻り、表示された `appsscript.json` の内容を `src/appsscript.json` の内容で完全に置き換えます。

### ステップ 3: シートのメニューから初期化

1. ソースを保存し、**スプレッドシートを再読み込み**します。配布テンプレートをコピーした場合も、コピー先のシートを開き直してください。
2. メニューの **GAS Artifact Hub → 初回セットアップ** を選択します。関数や一時ファイルの追加は不要です。
3. 初回はGoogleの権限承認画面で、利用するアカウントと要求権限を確認して許可します。承認後に入力画面が出ない場合は、もう一度メニューを選びます。
4. 保存先フォルダのIDを入力します。
   - **IDを入力**: 指定したフォルダ自体をHTML保存先として使用します。書込み可能で、一般社員へ直接共有していない専用フォルダを指定してください。URLの `folders/` の直後がIDです。URL全体は入力しません。
   - **空欄でOK**: 実行アカウントのマイドライブ直下に `GAS-Artifact-Hub-Storage` フォルダを新規作成します。同名の既存フォルダは流用しません。
   - **キャンセル**: 初期化せず終了します。指定IDが不正、またはフォルダにアクセスできない場合も、自動作成には切り替えません。
5. 「セットアップ完了」が表示されたら、以下の5シートと、通知に表示された保存先フォルダIDを確認します。
   - `system_config`（システム環境設定）
   - `artifacts`（アーティファクト台帳）
   - `versions`（バージョン情報台帳）
   - `acl`（アクセス権限一覧）
   - `audit_log`（変更監査ログ）
6. 空の初期シート（`シート1` / `Sheet1`）は削除され、各管理シートの列数は必要な数（3・11・9・5・6列）に整理されます。データ・数式・メモがある初期シートや余剰列、独自のシートは削除しません。

再実行では確認画面のあと、既存の保存先・設定・台帳を維持して空のシートと列を整理します。停止中のシステムを勝手に再開しません。既存データの保存先を移す機能ではないため、保存先変更は別途バックアップと移行が必要です。

`SPREADSHEET_ID` は自動保存されます。セットアップの本体とメニュー処理は末尾 `_` の非公開関数であり、WebアプリのブラウザRPCには公開しません。`onOpen` はメニュー追加だけを行います。

### ステップ 4: システム設定値の確認
スプレッドシートの `system_config` シートを開き、以下のキーと値が設定されていることを確認します：
- `SYSTEM_ENABLED`: `true`（稼働中）
- `STORAGE_FOLDER_ID`: 指定した専用フォルダ、または空欄時に自動生成したフォルダの ID
- `ALLOWED_DOMAIN`: 管理者アカウントのドメイン名（小文字）
- `MAX_HTML_SIZE_KB`: `1024`（HTML サイズ上限 1MB）

> **注意**:
> キー名を変更したり行を重複させないでください。
> 別のスプレッドシートから設定行をコピーして `STORAGE_FOLDER_ID` などの古い ID を流用しないでください。

### ステップ 5: Web アプリのデプロイ
1. 本番13ファイルと `appsscript.json` が配置されていることを確認します。旧手順で追加した `RunSetupOnce.gs` / `runSetupOnce` がある場合は削除・保存してから進みます。
2. Apps Script エディタの右上にある **デプロイ → 新しいデプロイ** をクリックします。
3. 種類の選択（歯車アイコン）で **ウェブアプリ** を選択します。
4. 以下の通り設定します：
   - **説明**: 初回本番デプロイ（任意）
   - **次のユーザーとして実行**: **自分 (USER_DEPLOYING)**
   - **アクセスできるユーザー**: **組織内の全員 (DOMAIN)** （※「全員」や「自分のみ」を選ばないでください）
5. **デプロイ** ボタンをクリックします。
6. 表示された **ウェブアプリの URL**（末尾が `/exec` のもの）をコピー・記録します。

## 3. clasp によるコード配置（開発者・CI 向け任意手順）

手動コピペの代わりに Google 公式の CLI ツール [clasp](https://github.com/google/clasp) を用いて配置することも可能です。

1. 作業フォルダで `.clasp.example.json` をコピーして `.clasp.json` を作成します。
2. Apps Script プロジェクトの設定画面から「スクリプト ID」を取得し、`.clasp.json` の `scriptId` に設定します（`rootDir` は `src` のままにします）。
3. ターミナルで以下を実行します：
   ```sh
   clasp login
   clasp status
   clasp push
   ```
4. `clasp status` で対象が `src/` の本番ファイルだけであることを確認してから push してください。
5. `clasp clone` を既存の `src/` に向けて実行してローカルファイルを上書きしないでください。
6. 配置後はシートを再読み込みし、上記「ステップ 3」以降のメニューによる初期化とデプロイを実施します。一時実行関数の追加は不要です。

## 4. 本人識別の実環境検証（一般社員アカウントでの確認）

Web アプリを全社へ配布する前に、**一般社員アカウント（DB や保存フォルダのアクセス権を持たない別アカウント）** を用いて初期検証を実施します。

1. 一般社員のアカウントでブラウザを開き、デプロイした `/exec` URL にアクセスします。
2. ポータル画面が正常に表示され、右上にその社員の正しいメールアドレスが表示されることを確認します。
3. スプレッドシートや保存フォルダをその社員へ直接共有していないにもかかわらず、画面が正常にロードされることを確認します。
4. 網羅的な検証項目については、[実環境受入試験計画書](acceptance.md) を実施してください。

### 【技術補足】Session 仕様と実行権限について
- 本システムは `Session.getActiveUser().getEmail()` を用いて利用者のメールアドレスを取得し、厳格なアクセス制御を行っています。
- 同一 Workspace ドメイン内かつ「組織内の全員」に公開された Web アプリでは、通常このメソッドでアクセス者のメールアドレスが取得できますが、万が一組織ポリシーやブラウザ環境により取得できない場合は、システムが fail-closed（安全側に倒して拒否）し、処理を遮断します。
- `getEffectiveUser()` はデプロイ所有者（管理者自身）を返すため、本人識別の代替としては絶対に使用しません。
- 「アクセスしているユーザーとして実行」に変更すると、スプレッドシートや Drive も一般社員自身の権限でアクセスする必要が生じ、DB を全社員へ直接共有しなければならなくなるため、本システムでは採用しません。
- 参照: [Google Apps Script Session 仕様](https://developers.google.com/apps-script/reference/base/session)、[Web アプリの権限モデル](https://developers.google.com/apps-script/guides/web#permissions)

## 5. コピー配布テンプレートについて

他の組織や自社の別部門へ環境を配布する場合、既存のスプレッドシートをそのまま共有・コピーさせると自社のデータや ID が混入する危険があります。安全な配布用テンプレートの作成手順は [配布用テンプレート作成手順](template-release.md) を参照してください。
