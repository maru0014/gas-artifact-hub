# Phase 2 ロードマップと技術検討書（Roadmap & Design Considerations）

本ドキュメントは、GAS Artifact Hub の次期フェーズ（Phase 2）において検討されている「いいね（Reactions）」機能および「コメント（Comments / Feedback）」機能の設計方針、アーキテクチャ上の課題、および解決アプローチを整理したものです。

> **注意**:
> 本ドキュメントは**設計・技術検討のための資料であり、現フェーズでの実装は開始しません**。
> Google Apps Script（GAS）および Google スプレッドシートの特性（実行クォータ、排他ロックの競合、同時書込み性能）を慎重に考慮したアーキテクチャ設計が必要です。

---

## 1. 機能要件と設計方針

### 1.1 「いいね（Reactions / Votes）」機能

利用者が有用なアーティファクトに対して評価・リアクションを投票できる機能です。

| 項目 | 要件と設計方針 |
| --- | --- |
| **1 人 1 票の整合性** | `Session.getActiveUser().getEmail()` に基づき、同一アーティファクトに対して 1 ユーザー 1 票のみ有効とします（トグル操作による取消・再投票を許容）。 |
| **集計と表示** | ポータルの一覧カードおよびビューアのヘッダーに総いいね数を表示します。 |
| **閲覧権限との整合** | アーティファクトの公開範囲（`visibility`）および ACL を満たし、閲覧権限（`canView`）を持つユーザーのみが投票・閲覧できます。 |

### 1.2 「コメント（Comments / Feedback）」機能

アーティファクトに対する利用者のフィードバック、改善要望、動作報告を投稿・閲覧できる機能です。

| 項目 | 要件と設計方針 |
| --- | --- |
| **閲覧・投稿権限** | アーティファクトの閲覧権限を持つユーザーのみがコメントを閲覧・投稿できます。`private` なアーティファクトのコメントは外部へ一切漏洩させません。 |
| **機密情報・コードの扱い** | コメント欄に機密情報や長大なソースコード、攻撃コードが投稿されるリスクがあるため、文字数制限（例: 最大 1,000 文字）、プレーンテキスト化、および Stored XSS 防止（`textContent` 描画）を徹底します。 |
| **モデレーションと削除** | 投稿者本人による削除に加え、アーティファクトの管理責任者（custodian）およびシステム管理者による不適切コメントの強制削除（モデレーション）権限を付与します。 |
| **保持期間と論理削除** | コメントは監査ログと同様に論理削除（`status = deleted`）とし、スプレッドシート上の行履歴を残すか、または一定期間（例: 1 年）経過後のアーカイブ方針を定めます。 |

## 2. GAS / Sheets 実行基盤における技術課題と対策

### 課題 1: スプレッドシート書込みコストと排他ロック競合
- **現象**: 「いいね」や「コメント」の投稿ごとにスプレッドシートへ直接行追加（`appendRow`）やセル更新を行うと、`LockService` の排他ロック時間が増大し、多数のユーザーが同時にアクセスした際に `LOCK_TIMEOUT`（ロック取得タイムアウト）が頻発します。
- **対策**:
  - **集計値のキャッシュ化**: 総いいね数は `CacheService`（TTL: 5〜10分）にキャッシュし、一覧表示時の Sheets 読込みを抑止。
  - **バッチ書込み・遅延集計の検討**: 高頻度な「いいね」更新は、専用シートへの追記に特化させるか、時間ごとの非同期トリガーで集約集計するアーキテクチャを検討。

### 課題 2: シート容量制限（1,000 万セル上限）
- **現象**: コメントやリアクション履歴が無制限に増え続けると、スプレッドシートの全体セル数上限（現行 1,000 万セル）やファイルサイズ上限に近づき、全体のパフォーマンスが低下します。
- **対策**:
  - コメントシート（`comments`）およびリアクションシート（`reactions`）を定義する際、不要な空行・空列を定期的に整理・パージする保守スクリプトを計画。

## 3. 通知（Notifications）の検討

コメント投稿や新バージョン公開時の通知機能は、全社一斉送信によるノイズ化や GAS のメール送信クォータ（1 日最大 100〜1,500 通）の枯渇を防ぐため、以下の選択方式を検討します：

1. **オプトイン方式**:
   - アーティファクトの「通知を受け取る」をオンにしたユーザーのみに通知。
2. **通知チャネルの分離**:
   - Gmail の直接送信だけでなく、Google Chat の Incoming Webhook や Slack 連携など、組織のチャットツールへの通知を選択可能とする。
3. **バッチまとめ通知**:
   - コメントが連続投稿された場合、即時送信ではなく 1 時間〜1 日単位でまとめるダイジェスト通知の導入。
