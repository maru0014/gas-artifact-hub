# 運用・保守マニュアル

Google Apps Script（GAS）Webアプリとして導入した GAS Artifact Hub の日常運用、緊急停止、管理責任者の引継ぎ、バックアップ・復旧、アップデート手順をまとめます。

## 日常運用と状態確認

本システムは Google スプレッドシート（設定・台帳・ACL・監査ログ）と Google Drive（HTML実体ファイル）で動作します。

- **WebアプリURL**: デプロイ時に発行された `/exec` URL
- **スプレッドシート（DB）**: セットアップ時に作成されたスプレッドシート
- **専用保存フォルダ**: Google Drive 上の `GAS-Artifact-Hub-Storage` フォルダ

管理者は、スプレッドシートの `system_config`、`artifacts`、`audit_log` を定期的に確認し、異常なエラーや不正な操作がないかを監視します。

## 緊急停止の手順

障害発生時や不正なアーティファクトが検出された場合、管理者はスプレッドシートから即座に停止操作を行えます。

### 1. システム全体の緊急停止

システム全体をメンテナンスまたは緊急停止状態にし、すべての新規API要求と閲覧を遮断します。

1. 管理用スプレッドシートを開きます。
2. `system_config` シートを選択します。
3. `SYSTEM_ENABLED` 行の `value` 列（B列）の値を `true` から **`false`** に変更します。
4. これ以降、ポータル画面・ビューア画面からのすべてのデータ取得・更新要求は `システムは現在メンテナンスまたは緊急停止中です。` というエラーを返し、処理が遮断されます。
5. 再開する場合は、`value` 列を `true` に戻します。

### 2. 特定アーティファクトの個別停止

特定アーティファクトのみを非公開・停止状態にし、アクセスを遮断します。

1. 管理用スプレッドシートを開きます。
2. `artifacts` シートを選択します。
3. 対象アーティファクトの行を特定します（`artifact_id` または `title` で検索）。
4. `status` 列（H列）の値を `active` から **`disabled`** に変更します。
5. これ以降、該当アーティファクトの閲覧（ビューア画面）、編集、新版投稿、設定変更はすべて `アーティファクトが見つかりません。` または権限エラーとなり遮断されます。
6. 監査・調査が完了し再公開する場合は、`status` 列を `active` に戻します。

### 【重要制約】実行中・ダウンロード済みのHTMLについて

> **注意**:
> スプレッドシート側で `SYSTEM_ENABLED = false` や `status = disabled` に設定した後に効果を発揮するのは、**その後に発生する新しい読み込み要求やAPI呼び出し**です。
> **すでに利用者のブラウザ上でロードされ実行中のHTMLや、手元のPCにダウンロード保存されたHTMLファイルを、サーバー側から強制終了・回収することは技術的に不可能です。**
> 情報漏洩等の緊急インシデントが発生した場合は、ネットワーク遮断や利用者への注意喚起など、組織のセキュリティ対応規程に沿った一次対応を並行して実施してください。

## 管理責任者（Custodian）の引継ぎ

アーティファクトの作成者が異動・退職する場合、管理者が管理責任者（custodian）を変更して運用権限を引き継ぎます。

### 引き継ぎ手順

1. 管理用スプレッドシートを開き、`artifacts` シートを選択します。
2. 対象アーティファクトの行を特定します。
3. `custodian` 列（E列）のメールアドレスを、新しい管理責任者のGoogle Workspaceアカウントのメールアドレスに変更します（小文字で入力）。
4. `acl` シートを選択し、新しい管理責任者の `role` を `editor` として追加（または既存行を更新）します。
5. 旧管理責任者のeditor ACLを削除します。`all` では同一ドメインの旧管理責任者も引き続き閲覧でき、viewer ACLは不要です。`list` ではACL削除後は閲覧不可となり、閲覧だけを継続する場合は削除の代わりに `viewer` へ変更します。旧管理責任者を `editor` のまま残すと、custodian変更後も編集権限が残ります。
6. 新任の管理責任者で編集・管理できることと、旧管理責任者では新版投稿・設定変更が拒否されることを、それぞれの実アカウントで確認します。閲覧の期待は `all`（閲覧可）、`list` のACLなし（閲覧不可）、`list` のviewer（閲覧可）に分けます。`private` は新custodianだけが閲覧・編集できます。

> **設計規律**:
> `created_by` 列は監査・履歴情報（作成当時の記録）であるため変更しません。
> アクセス権限・設定変更権限の判定は現在の `custodian` および `acl` シートの正本データに基づいて行われます。

## バージョン（公開版）の切替と緊急ロールバック

### 通常の版切替（UI操作）

編集者権限を持つユーザーは、ビューア画面または設定モーダルから、過去にアップロードされたバージョン一覧を確認し、公開バージョン（`current_version_id`）を切り替えることができます。

### 管理者による緊急ロールバック（スプレッドシート操作）

UIから操作できない場合や管理者が強制的に過去バージョンへ巻き戻す場合：

1. 管理用スプレッドシートの `versions` シートを開きます。
2. 対象アーティファクトの `artifact_id` で絞り込み、戻したい正常なバージョンの `version_id`（A列）をコピーします。
3. `artifacts` シートを開き、該当行の `current_version_id` 列（F列）にその `version_id` を貼り付けます。
4. `updated_at` 列（J列）を現在の日時（ISO 8601形式）に更新します。
5. 次回のアクセス時から、即座に指定したバージョンのHTMLが配信されます。

> **キャッシュに関する注記**:
> 90KB以下のHTML実体は高速化のため `CacheService`（TTL: 最大10分）にキャッシュされます。
> 公開版の `current_version_id` はアクセスごとにスプレッドシートから読み、HTMLキャッシュは `version_id` とSHA-256の組み合わせで分離されます。そのため、ロールバック後の次回要求では指定した版のHTMLが選択され、同一版のキャッシュが存在する場合もその版と同じ内容が返ります。ブラウザのスーパーリロードや `SYSTEM_ENABLED` の切替ではScript Cacheは削除されません。現在、管理者がScript Cacheを強制削除する運用機構はないため、キャッシュ自体の異常が疑われる場合はTTL満了後に再確認するか、通常の新版アップロードと版切替で別のキャッシュキーを使用してください。

## デプロイの更新とロールバック

本番プログラム（`src/`）の修正やアップデートを適用する手順です。

### 1. デプロイの更新

URL（`/exec`）を変更せずにプログラムを更新します。

1. スプレッドシートから **拡張機能 → Apps Script** を開きます。
2. 更新されたコード（`.gs` / `.html`）を反映します（手動更新または `clasp push`）。
3. 画面右上の **デプロイ → デプロイを管理** を開きます。
4. 現在稼働中のデプロイ（種類：ウェブアプリ）を選択し、右上の **編集（鉛筆アイコン）** をクリックします。
5. 「バージョン」のドロップダウンから **新バージョン** を選択し、説明欄に修正内容を記入します。
6. **デプロイ** をクリックします。
7. WebアプリのURLは変わらないため、社内周知済みのURLをそのまま利用できます。

### 2. デプロイのロールバック

更新後に問題が発生した場合、直前のバージョンへ即座に戻す手順です。

1. Apps Script エディタの **デプロイ → デプロイを管理** を開きます。
2. 対象のデプロイを選択し、**編集（鉛筆アイコン）** をクリックします。
3. 「バージョン」のドロップダウンから、問題発生前の以前の安定バージョン番号を選択します。
4. **デプロイ** をクリックします。
5. 即座に以前のプログラムコードで稼働が再開されます。

## バックアップとリストア

### 保存補償が失敗した場合（ROLLBACK_FAILED）

1. エラーが表示された要求を繰り返し送らず、対象アーティファクト、操作時刻、操作内容を記録します。
2. `SYSTEM_ENABLED` を `false` にし、追加のアプリ書込みを止めます。既に進行中の要求が完了し得るため、実行状況も確認します。
3. 台帳5シートと保存フォルダを退避し、`artifacts.current_version_id`、対応する `versions` 行とDrive実体、ACL、監査を照合します。保持された新規Driveファイルを確認前に削除しないでください。
4. 整合するバックアップまたは確認済みの版とACLへ復元します。補償失敗時は監査ログも完全とは限らないため、監査だけで保存成功を判定しません。
5. 対象版の読出し、権限、設定保存を検証環境で確認し、復旧内容を記録したうえで稼働を再開します。自動補償で必ず復元できる保証はありません。

### 1. バックアップ対象

1. **スプレッドシート（メタデータ正本）**:
   - `system_config`, `artifacts`, `versions`, `acl`, `audit_log` の全データ。
   - スプレッドシート自体の「コピーを作成」または定期エクスポート（Excel/CSV形式）を実施。
2. **Google Drive 保存フォルダ（実体ファイル）**:
   - `GAS-Artifact-Hub-Storage` フォルダ内のすべての `.html` ファイル。
   - Google Drive のフォルダダウンロード等で定期バックアップを保存。

### 2. リストア手順と注意点

- スプレッドシートを過去のバックアップから復元した場合、スクリプトプロパティの `SPREADSHEET_ID` が復元先のスプレッドシートIDと一致していることを確認してください。
- `versions` シートに記録されている `drive_file_id` が、Google Drive上の実体ファイルと紐づいている必要があります。Driveフォルダを新規作成して中身を再配置した場合はファイルIDが変動するため、可能な限り既存のDriveファイル・フォルダを保持・復元してください。

## 監査ログとデータの物理削除方針

### 1. 監査ログの不変性

- すべての作成、版更新、版切替、メタデータ更新、ACL変更、削除操作は `audit_log` シートに記録されます。
- システムのプログラムからは追記（append）のみを行い、改ざん・更新処理は実装されていません。
- ※ただし、スプレッドシートの編集権限を持つ管理者自身による手動変更はGoogle Sheetsの仕様上防げないため、管理者は監査対象として信頼される運用主体となります。

### 2. 論理削除と物理削除（データ消去）

- **UIからの削除操作**:
  - Web UIからアーティファクトを削除した場合、`artifacts` シートの `status` が `deleted` になり、`deleted_at` にタイムスタンプが記録されます（論理削除）。
  - 過去のバージョンファイルやDrive上の実体HTML、監査ログは即座には消去されません。
- **物理削除（完全消去）が必要な場合**:
  - 機密情報や個人情報の誤投稿、GDPR等の法的要請により完全消去が必要な場合、管理者が以下の手順で物理削除を手動実行します：
    1. `artifacts` シートから該当アーティファクトの行を削除（または退避）。
    2. `versions` シートから該当アーティファクトに紐づくすべての行を削除し、記載されている `drive_file_id` を控える。
    3. `acl` シートから該当アーティファクトの行を削除。
    4. Google Driveの `GAS-Artifact-Hub-Storage` フォルダ内から該当ファイルを検索し、ゴミ箱へ移動した上でゴミ箱を完全に空にする。
    5. `audit_log` シートに物理削除を実施した理由と日時・担当者を追記記録する。
